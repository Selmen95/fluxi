# Fluxi: purchasing automation with a tool-using agent (showcase)

A compact, runnable showcase of the core ideas behind **Fluxi**, a purchasing platform for a retail distribution group: ingesting unstable Excel exports, computing replenishment proposals, checking supplier invoices, and orchestrating it all through an agent loop with tools and a human approval gate.

Everything runs offline on **synthetic data** generated by a seeded script.

## Context

Fluxi is a real project delivered through Opsen, a studio building B2B software for retail distribution groups. It was delivered to a retail distribution group under a signed quote and put into production.

This repository is **not** that codebase. It is a reduced, rewritten showcase of representative modules, built for public viewing. Client names, store names, suppliers, real figures, real files and the real database schema are deliberately excluded. The data is synthetic and the numbers below are produced by the code in this repository, not by the client's data.

## What is inside

| Module | What it does |
| --- | --- |
| `synth.py` | Seeded world generator (stores, SKUs, suppliers, stock, 90 days of sales, purchase orders, invoices with injected anomalies). Also writes the sales history as three deliberately unstable Excel layouts. |
| `ingest.py` | Detects the layout of each file (long with localized headers and decimal commas, wide with one column per day and a footer total, one sheet per store with text units and duplicates) and maps them to one canonical table with a per-file quality report. |
| `replenishment.py` | Reorder rules: demand and variability over a rolling window, safety stock for a service level, pack-size rounding, supplier minimum order value with an urgency override. |
| `invoices.py` | Invoice control against purchase orders: unknown SKU, over-billed quantity, price drift beyond tolerance, header total mismatch, duplicate invoices. |
| `agents.py` | Orchestrator with a tool registry, argument validation, step budget, trace, and an approval gate on side-effecting tools. The planner is pluggable. |
| `cli.py` | End-to-end demo. |

## Architecture

```
 seeded generator
        |
        v
 3 Excel layouts --> ingest (sniff layout, normalize, dedupe, report)
                          |
                          v
                 canonical sales table
                          |
         +----------------+----------------+
         v                                 v
  replenishment rules              invoice control (PO matching)
         |                                 |
         +----------- tools ---------------+
                          |
                  agent orchestrator
        (validate args, step budget, trace,
         approval gate on side effects)
                          |
                 human approves or rejects
```

The agent loop is model-agnostic. The shipped `ScriptedPlanner` is rule-based so tests are deterministic and need no network or API key. A hosted-LLM planner would implement the same one-method `Planner` interface; the guardrails live in the orchestrator, not in the model.

## Stack

Python 3.10+, pandas, numpy, openpyxl, pytest.

## Run it in 3 commands

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
fluxi-demo && pytest
```

## Results on synthetic data

Output of `fluxi-demo` (seed 42):

- **Ingestion**: three files, 21,600 canonical rows after cleaning. The result is checked to be identical to the generator's ground truth (blank rows, a footer total and 12 duplicated rows removed).
- **Replenishment**: 231 proposed lines, all released in the default configuration. The hold and urgent-release paths are covered by unit tests on crafted cases.
- **Invoice control**: 15 injected anomalies (five kinds, including duplicates), 15 flagged, precision 1.00 and recall 1.00. This is by construction, since the anomalies are injected by the same generator family; it demonstrates that the checks work, not how they would perform on real invoices.
- **Agent**: the replenishment goal runs two tool calls; the purchase order drafting step stops at `pending_approval` unless an approver callback is supplied.

## Limits

- Synthetic data is cleaner than real data: no encoding problems, no merged cells, no ambiguous product codes, no unit-of-measure conversions.
- Demand is the mean over a window. There is no forecasting in this showcase (the sibling project covers that).
- Supplier constraints are reduced to pack size and a minimum order value. No price breaks, calendars or truck-load optimization.
- The scripted planner follows a fixed policy; it demonstrates the orchestration contract, not LLM reasoning quality.
- Invoice metrics are on injected anomalies and say nothing about real-world precision.
